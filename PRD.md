# Car Dealership Inventory System: Implementation Blueprint

Six phases, one repository, one primary coding agent, automated verification throughout.

No Bee orchestration, mandatory agent ping-pong, or artificial development cycles. Use the strongest available coding model, but preserve genuine TDD evidence because Incubyte explicitly requires it.

## 1. Architecture and technology decisions

The browser must never bypass the required backend API.

| Component                 | Choice                                          |
| ------------------------- | ----------------------------------------------- |
| Frontend                  | React + TypeScript + Vite + Tailwind            |
| Backend                   | Node.js + TypeScript + Express                  |
| Database                  | PostgreSQL (Supabase for preview/production)    |
| Authentication            | JWT, bcrypt password hashing, database roles    |
| Validation                | Zod                                             |
| Backend tests             | Vitest + Supertest + database integration tests |
| Frontend tests            | Vitest + React Testing Library                  |
| End-to-end/security tests | Playwright Test                                 |
| Hosting                   | Vercel                                          |
| CI                        | GitHub Actions                                  |

Why this stack: it satisfies the allowed technology choices and keeps frontend and backend in one language. Supabase supplies persistent PostgreSQL; Express owns the required REST endpoints. Supabase is a database here, not a replacement for the backend.

### Database environments

| Environment         | Database                                          | Purpose                                 |
| ------------------- | ------------------------------------------------- | --------------------------------------- |
| Local dev and tests | `postgres:16` in Docker                           | Fast, disposable, no secrets            |
| CI                  | `postgres:16` GitHub Actions service container    | Same migrations, no cloud dependency    |
| Vercel preview      | Supabase test project                             | Full deployed Playwright suite          |
| Vercel production   | Supabase production project (demo data)           | Controlled live verification            |

Migrations are plain SQL in `db/migrations/`, applied by one script to every environment. No environment-specific schema.

### Deployment details that matter

- One Vercel project: Vite static assets plus an Express-backed API function. Verify routing in P1, not after everything is built.
- Serverless database access goes through Supabase's transaction pooler, with a small application-side pool and no named prepared statements.
- Database credentials stay server-side. Use least-privilege access where practical.
- Test and production data are separate. Destructive automated tests never run against production inventory.
- Authentication and authorization live in Express. Public registration never grants administrator privileges.

Custom JWT authentication is a deliberate choice, not a PDF requirement. Supabase Auth is viable but would need adapting to the specified register/login endpoints.

### Implementation decisions (not specified by the PDF)

Define these once, document them in the README, and test them consistently.

| Decision            | Choice                                                                      |
| ------------------- | --------------------------------------------------------------------------- |
| Vehicle ID          | UUID, generated by the database                                             |
| Price               | `numeric(12,2)`, `CHECK (price >= 0)`; parsed from string at the repository |
| Quantity            | `integer`, `CHECK (quantity >= 0)`                                          |
| Purchase quantity   | One unit per `POST /purchase` call                                          |
| `POST`/`PUT` access | Admin only (frontend assigns them to admins); documented policy decision    |
| Listing             | Includes zero-stock vehicles so the disabled purchase state is visible      |
| Password policy     | Minimum 8 characters; bcrypt hash                                           |
| JWT                 | Short expiry (e.g. 1 hour), no refresh token; 401 on expiry                 |
| Token storage       | `localStorage`; logout clears it client-side                                |
| First admin         | Seed script reads admin email/password from environment variables           |
| Error shape         | `{ error: { code, message } }`; no stack traces or SQL in responses         |
| Status codes        | 400 validation, 401 unauthenticated, 403 forbidden, 404 missing, 409 conflict/out of stock |

## 2. Six implementation phases

| Phase                         | Scope                                                                            | Acceptance criteria                                                                                                                  |
| ----------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| P1. Foundation                | Repository, TypeScript, Express, Vite, migrations, CI, deployment smoke test     | Build/typecheck passes; real PostgreSQL connection works; API and SPA routing work locally and on Vercel                             |
| P2. Authentication            | Register, login, password hashing, JWT, roles, admin seed                        | Valid credentials work; invalid credentials fail; protected routes reject invalid tokens; normal users cannot become admins          |
| P3. Vehicle management        | CRUD, list, search, filtering                                                    | All specified vehicle endpoints respond correctly; admin restrictions hold; search filters compose; data survives restarts           |
| P4. Inventory integrity       | Purchase, restock, stock validation                                              | No negative inventory; out-of-stock purchases fail; concurrent purchases cannot oversell; admin-only restock enforced                |
| P5. Frontend                  | Design direction, auth, inventory, admin screens, responsive layout              | All required actions work through the API; zero-stock purchases disabled; mobile/tablet/desktop usable; failures handled clearly     |
| P6. Verification and delivery | Playwright, security review, production deployment, documentation               | All mandatory deliverables present; CI green; deployed browser/API failure scenarios verified; no unresolved critical defects        |

P1 includes a minimal deployment to surface platform integration problems early. P6 handles the final release.

### Completion gate after every phase

- Phase acceptance criteria pass.
- New behavioral tests demonstrably failed before implementation, then passed.
- Full test suite, typecheck, lint, and build pass.
- Commits follow the convention in section 3 and carry the AI co-author trailer.
- README and `PROMPTS.md` are updated.
- No known critical security, data-integrity, or regression issues remain.
- The phase's commits are pushed (push after every major chunk; see `HANDOVER.md`).

## 3. Git and TDD conventions

Commit message prefixes narrate Red-Green-Refactor:

| Stage    | Prefix                 | Content                                         | Test state |
| -------- | ---------------------- | ----------------------------------------------- | ---------- |
| RED      | `test: … (red)`        | Failing behavioral tests only                   | Failing    |
| GREEN    | `feat: … (green)`      | Minimal implementation that makes them pass     | Passing    |
| REFACTOR | `refactor: …`          | Real structural improvement, behavior unchanged | Passing    |
| Other    | `chore:`/`docs:`/`ci:` | Tooling, documentation, configuration           | Passing    |

- Establish this from the first backend feature. Retrofitting RED/GREEN history afterwards would undermine the assessment.
- Refactor only where it improves the code. Never fabricate refactor commits.
- CI runs on pushes. Pushes happen after each green chunk, so the tip of every push is green. RED commits stay in history as intermediate commits, and the README explains this.
- Every AI-assisted commit ends with two blank lines, then the trailer the PDF requires:

  ```
  Co-authored-by: Claude Opus 5.5 <noreply@anthropic.com>
  ```

  Credit each model that actually contributed (e.g. add a Codex/GPT trailer when it wrote code). Never add session URLs or other session/account identifiers.

## 6. SOLID and clean engineering

Apply SOLID proportionately. The PDF asks for the principles, not a textbook demonstration of each.

| Principle                 | Practical application                                                       |
| ------------------------- | --------------------------------------------------------------------------- |
| S — Single Responsibility | Routes handle HTTP; services handle business rules; repositories handle SQL |
| O — Open/Closed           | Keep extensions simple; no premature plugin architecture                    |
| L — Liskov Substitution   | Avoid inheritance unless needed; don't invent subclasses to demonstrate it  |
| I — Interface Segregation | Small contracts around genuine dependencies                                 |
| D — Dependency Inversion  | Inject the database pool/repositories where it improves testing             |

Also: explicit TypeScript types, shared Zod schemas where appropriate, parameterized SQL, centralized error handling, clear naming, and comments that explain intent rather than restate code.

Avoid generic base repositories, excessive interfaces, CQRS, event sourcing, microservices, and abstractions for hypothetical requirements. Route → service → repository is sufficient.

## 7. Testing strategy

The highest-value tests are failure cases that could corrupt inventory or bypass authorization.

| Area           | Essential non-happy-path scenarios                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Authentication | Duplicate registration, invalid input, incorrect password, missing/expired/tampered JWT, role escalation attempt             |
| Vehicle CRUD   | Invalid IDs, missing records, invalid price, fractional/negative quantity, unknown fields, unauthorized operations           |
| Search         | Empty results, combined filters, case variation, invalid price bounds, malformed inputs, injection-like strings              |
| Purchasing     | Zero stock, exactly one remaining, repeated requests, simultaneous purchases, nonexistent vehicle                            |
| Restocking     | Unauthorized user, zero/negative/fractional input, nonexistent vehicle, integer overflow                                     |
| Database       | Connection failure, constraint violation, persistence after restart, rollback/data integrity                                 |
| Frontend       | API timeout, 401 session expiry, 403 permission error, 409 out-of-stock conflict, loading/empty/error states                 |

### Highest-priority concurrency test

Start with vehicle quantity = 1 and send 20 simultaneous purchase requests.

Pass condition: exactly one succeeds, the others return 409, and the final database quantity is zero.

Implement purchasing as a single conditional update (`UPDATE … SET quantity = quantity - 1 WHERE id = $1 AND quantity > 0 RETURNING …`), never a read-modify-write in JavaScript.

Restocking validates positive integer quantities and rejects results beyond the column's range.

### Test layers

- Unit: input validation and service rules.
- Integration: real Express requests via Supertest against a real PostgreSQL database.
- Database: constraints and simultaneous inventory modifications.
- Component: form validation, disabled buttons, permission-based rendering.
- E2E: complete user and administrator workflows on the running app.

Report coverage, but don't impose an arbitrary 95–100% target. Meaningful branch and failure-path coverage matters more.

## 8. Automated Playwright suite

Use `@playwright/test` as a reproducible runner, not an agent that opens a browser and claims everything looks right.

| Suite               | Scenarios                                                                |
| ------------------- | ------------------------------------------------------------------------ |
| `auth.spec.ts`      | Register, login, logout, invalid credentials, expired session            |
| `inventory.spec.ts` | Listing, searching, filtering, purchase, zero-stock UI                   |
| `admin.spec.ts`     | Add, edit, delete, restock, role-sensitive UI                            |
| `failures.spec.ts`  | Server errors, unavailable API, validation failures (via `page.route`)   |
| `security.spec.ts`  | Direct unauthorized API calls, forged/invalid tokens, tampering attempts |

Browser projects: Chromium desktop and WebKit mobile.

Configuration:

- Environment-driven `BASE_URL`.
- Separate user/admin authentication fixtures.
- Isolated test accounts and inventory records per test.
- Retries only for diagnosing transient failures, never to hide defects.
- Screenshots and traces on failure.
- HTML plus machine-readable (JSON/JUnit) reports.
- Parallelism only for tests with isolated server-side state.

Never commit Playwright authentication-state files; they contain reusable credentials.

## 9. Security testing and independent review

### What Playwright verifies

Playwright's API request context exercises security-sensitive endpoints independently of the frontend. Test that:

- User JWTs cannot invoke admin operations.
- Missing or corrupted tokens produce 401.
- Sending `role: "admin"` in request bodies cannot escalate privileges.
- Unexpected fields cannot overwrite privileged properties (mass assignment).
- SQL-injection-like input is treated as data.
- XSS-like vehicle text renders safely.
- Error responses leak no stack traces, credentials, or SQL details.
- Purchase/restock calls cannot violate quantity invariants.

These map to OWASP API Security Top 10 risks: broken authentication, object-property-level authorization, and function-level authorization.

### Independent security review

Run one focused, read-only review after P4 and one after P6:

1. Trace authentication and authorization across every protected endpoint.
2. Inspect database privileges, migrations, secrets, and SQL operations.
3. Examine data integrity, concurrency, dependencies, and error disclosure.
4. Return findings with file/line evidence, severity, exploit preconditions, and a concrete fix.
5. Rerun tests after fixes and verify closure.

An agent review supplements Playwright; neither amounts to a penetration test. Security tests that modify data run in a disposable environment. No autonomous agent gets unrestricted authority over the production database.

## 10. Deployed-app verification

**Preview (full verification):** run all Playwright UI, API, authorization, data-integrity, and failure-injection tests against the Vercel preview deployment and the Supabase test project. Use Vercel's automation bypass if preview protection is on.

**Production (controlled live verification):** real login, listing, search, role rejection, validation failures, out-of-stock behavior, and one purchase/restock cycle, using disposable fixtures with cleanup.

Run deployed tests from the commit intended for submission. Check console errors, failed network calls, mobile layout, and live database state. Record the deployment URL, commit SHA, test date, and results in `docs/test-report.md`.

Deployment is optional bonus credit in the brief; this plan makes it a required gate.

## 11. Evaluator access and AI logs

**Demo admin.** The production deployment runs on throwaway demo inventory. The README publishes a demo admin account and a demo user account for that deployment only, and `db/seed.ts` can reset the data. No real or reused credentials, and no database credentials, ever appear in the repository.

**`PROMPTS.md`.** The brief wants raw, unedited logs or public chat links, with no AI summaries.

- Prefer public share links for chat sessions (including the GPT session that produced this plan).
- For Claude Code / Codex transcripts, export them verbatim, with one documented redaction pass that removes only local filesystem paths, email addresses, session URLs, and secrets. State the redaction rule at the top of `PROMPTS.md`.
- Keep secrets out of prompts from the start so redaction stays minimal.

**Fresh clone.** The public repository must build and run from a fresh clone with only Docker, Node, and `.env.example`.
